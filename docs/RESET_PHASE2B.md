# Phase 2B monthly-to-ledger handoff

The monthly contribution preview and check-in remain planning/completion records. Neither creates investment units, purchase prices, costs, holdings, or portfolio history. After a completed check-in, the Plus monthly screen offers the existing dated-investment entry flow. The person supplies the investment date, actual units received, and optionally the actual PHP total paid. Planned PHP amounts appear only as context and are never copied into the actual-cost field or converted into units.

Each confirmed investment uses the Phase 1 idempotent ledger API. Partial recording and skipping are valid. An investment may be recorded in a different Manila calendar month than its UTC check-in month. The monthly activity list is filtered by the investment date and remains visible after an undone check-in; undo does not void ledger entries. Home Recent activity instead orders actual ledger events by update/record timestamp, so a newly recorded backdated investment is recent without pretending the investment happened today.

Basic Portfolio holding/activity access is available with tracking entitlement; monthly planning and check-in remain Plus, and Plan Alignment remains separately Plus-gated. The portfolio API omits target-comparison fields for a non-entitled owner. Production private-beta entitlement defaults were not changed.

The original monthly-to-ledger flow requires no migration. A separate, additive pending-recording migration (`20260927180503_pending_investment_recordings.sql`) is required before enabling the pending-recording API. A concrete monthly provider continuation first persists an owner-scoped pending recording, then opens the existing provider destination. On return, Home and the monthly screen offer a small resume cue. The user can record actual units through the Phase 1 ledger, wait, dismiss because they did not invest, or clear the cue because they already recorded elsewhere in Arbor. A successful ledger save precedes pending resolution; if resolution fails, the saved investment is retained and the cue can be cleared without recording it twice.

Pending is not a transaction, holding, cost, valuation, goal-progress event, snapshot, or evidence of provider execution. The pending row stores only owner, canonical product/provider, source, timestamps, and workflow status—no planned PHP or financial values. Home Recent activity remains ledger/check-in history, not provider-leaving clicks.

The complete intended beta loop is: monthly plan → **Continue with provider** → persisted unfinished recording → external provider → return **or** one privacy-safe reminder after roughly 24 hours → user enters actual units → Phase 1 ledger → pending resolves. Pending does not mean invested. A reminder does not mean invested, recommend or encourage another investment, change pending status, or change financial state. Actual units remain user-entered; planned PHP never becomes actual cost. No monthly batch-ledger association is required for this loop. Phase 2C has not started.

## Product-email worker and release gates

Resend is the transactional **product** email transport, isolated behind `EmailTransport`; it does not change Supabase Auth email templates or SMTP. The backend-only command is `python -m app.reminders pending-recordings`. Hosted reminders require a **separate** Render cron, hourly (`0 * * * *` UTC), not `arbor-market-data-refresh`. The worker uses a trusted Supabase operator key to claim reminder work and fetch the current account email through Auth Admin. Authenticated app requests have no claim/send permission. The worker cannot run from a browser and does not depend on the founder's laptop.

Required trusted environment-variable **names** for later enablement: `ARBOR_PRODUCT_EMAIL_ENABLED=true`, `SUPABASE_URL`, `RESEND_API_KEY`, `ARBOR_PRODUCT_EMAIL_FROM`, `ARBOR_APP_URL`, and either `SUPABASE_PRODUCT_EMAIL_KEY` or the existing backend-only `SUPABASE_MARKET_DATA_KEY`. The worker prefers the dedicated product-email name when present, but can reuse the already configured market-data operator key; the latter was verified to have Auth Admin access on Render without revealing its value. Either key must remain server-side and must never be reused as a public key. The sender validation accepts the founder's verified `mail.arbor.ph` subdomain. `ARBOR_APP_URL` must be an Arbor-owned HTTPS origin. With the enable flag absent/false or configuration incomplete, the worker does not send. The hosted cron and live email remain separate release gates.

One generic email covers all eligible pending items of one account; it contains no products, providers, amounts, units, holdings, goals, or projections. The subject is “Finish updating your Arbor portfolio.” Its conditional wording says to return **if** an investment was completed elsewhere and record actual units. The CTA goes only to `https://arbor.ph/#home/monthly` (or the same path on the configured Arbor origin), with no user or financial identifier or token. Existing authentication protects the destination.

The migration adds a trusted owner-level delivery record and links only items that are still pending and at least 24 hours old. A partial unique index, transaction-scoped advisory lock, short five-minute claim lease, and operator-only SQL functions prevent overlapping workers from claiming different products for the same owner. The worker checks current Auth email and revalidates database eligibility immediately before delivery. A successful send marks only the included still-pending items as reminder-covered; it does **not** resolve them. Each pending item can contribute to at most one successful email. A seven-day owner cooldown prevents a burst from separate later intents.

The DB stores a stable delivery ID and SHA-256 request fingerprint, not the recipient or message body. Resend receives `Idempotency-Key: arbor-pending-recording-reminder/<delivery-id>` and the same payload on retries. Resend documents a 24-hour idempotency window, so Arbor stops automatic retries after **23 hours from first attempt**, or three attempts, whichever comes first. Retries wait at least 15 minutes. An ambiguous network failure retains the same delivery/key; if the account email, sender, or message changes, the fingerprint mismatch stops automatic retries for operational review rather than risking a different request under the same key. An explicit accepted provider response is required before marking sent. A failure or crash cannot mark pending as invested. A resolution milliseconds after the final DB check but during the external HTTP call cannot be made atomic with the provider; the email remains conditional and contains no sensitive details.

The SQL contract was qualified on task-owned local PostgreSQL 17 with multiple independent connections; PGlite tests remain supplementary. Production email must remain disabled until the migration, deployment, trusted cron environment, and disposable-account hosted smoke are verified. Creating the cron does not itself authorize sending.
